0. 问题背景：电动卡车 + 死线 = 噩梦

你不是在解方程，你是在做调度员

星期一早 6:00。你是城市物流中心的调度员，面前有一张表：

  • 100 个待配送订单，散布在城市各处
  • 每个订单写着："请于 8:00–9:30 送达"（早于 8:00 没人收货，晚于 9:30 客户投诉）
  • 手上有 6 辆电动卡车，每辆能装 200 件货，电池能跑约 37 公里
  • 目标是：所有顾客准时送达，总行驶距离最短，总成本最低

你会怎么做？先在地图上把顾客分成 6 个片区，每辆车负责一片，这很自然。然后呢？让司机自己决定路线？司机会迷路。你会用导航软件去规划每片区的"最优路线"。 但问题来了：导航只管最短距离，它不管"9:30 之前必须到"。

这就是 EVRP-TW 的本质：你有 100 个带截止时间的点 + 6 辆有电池限制的车，你要给出一个"不迟到且总成本最低"的完整计划。

EVRP-TW 的形式定义

给定：

  • N 个顾客：每个顾客 i 有坐标 (x_i, y_i)、需求量 q_i、时间窗 [e_i, l_i]（最早服务时间 e_i，最晚服务时间 l_i，即 due_time）、服务时间 s_i
  • K 辆电动卡车：每辆容量 Q、电池容量 B（55 kWh）
  • M 个充电站：坐标 (x_cs, y_cs)，非线性充电函数 charge(soc_start, duration) → kWh
  • 1 个仓库 depot：所有卡车从这里出发，最终回到这里

目标：找到 K 条路线 R_1, ..., R_K，满足：

  1. 分区覆盖：每个顾客恰好在一条路线上
  2. 容量约束：每条路线总需求量 ≤ Q
  3. 时间窗约束：每条路线上每个顾客的实际到达时间 ≤ l_i（不迟到是硬约束）
  4. 电池约束：每条路线的耗电量不超过电池容量（允许中途充电）
  5. 最小化总成本：总行驶距离 + 充电成本 + 车辆使用成本

为什么这个问题难到让所有经典方法得 0 分？

EVRP-TW 天然包含三个互相嵌套的子问题：

子问题决策内容计算复杂度难点
Routing 路线规划谁分给哪辆车？每辆车走什么顺序？NP-hard (TSP 是特例)顾客数量增加 1，可能路线数量指数增长
Scheduling 时间调度路线顺序决定到达时间，能否满足所有 due_time？NP-hard (带时间窗的 TSP)顺序改变到达时间，迟到 = 硬违规，不可接受
Charging 充电决策什么时候充电？充多少？去哪充？NP-hard (FRVCP)充电站可能不在路线上，需要绕路；充电时间影响后续到达时间

如果把这三个问题揉在一起优化（经典做法），搜索空间大到不可想象。遗传算法、蚁群算法、变邻域搜索都试过，结果一致：距离能优化，但时间窗全部迟到（TW 可行性 0%–10%）。

我们的核心哲学：Decompose, then Repair (分解，再修复)

与其在一个巨大的、不可解的搜索空间中挣扎，不如把问题拆开：

  • POMO 神经网络负责"怎么走最近"（距离优化）— 这是它最擅长的事
  • Forward Insertion 修复算子负责"怎么走不迟到"（时间窗修复）— 这是手术式的精准操作
  • EV 评估模块负责"电够不够"（充电决策）— 独立于路由的后期验证

两个难题各自有成熟的工具，合在一起就解决了 EVRP-TW。分解 = 每个子问题用最合适的工具，修复 = 手术式解决子问题间的冲突。

2. Step 1 — Budget-Aware 聚类：最少干预，最多松弛

为什么先聚类？

POMO 是一个在 CVRP（约 20–100 个顾客）上预训练的神经网络模型。如果你把 200 个顾客直接丢给它，推理质量会严重退化。 聚类的本质是 Cluster-First, Route-Second 范式（Fisher & Jaikumar, 1981）：先把大问题拆成 K 个小问题，每个小问题 POMO 都能高质量求解。

核心原则：Minimal Intervention (最少干预)

好的聚类 = 空间紧凑 + 时间可行。但两者的优先级不同：空间紧凑 > 时间可行。

为什么？因为空间紧凑的组，路线就短 → 总旅行时间少 → 更容易满足时间窗。而且如果 POMO 路线中有迟到，后面的 Forward Insertion 可以修复。空间优化和时间优化在这里是"一致"的，不是矛盾的。

我们的策略：

  • 先用纯空间 K-means++ 聚类，产生最优的空间分组
  • 仅当某个组的 EDD（最早截止时间优先）模拟路线所需时间超过该组 TW 时间预算的 75% 时，才按时间窗分裂
  • 75% 阈值保留了 25% 松弛给 Forward Insertion — 这是 Theorem 1 的工程应用

算法三步走

Step 1: 纯空间 K-means++

# 初始化: K-means++ 智能选择初始中心点 (远离彼此)
centers = kmeans_plus_plus_init(customers, k)

# 迭代: 标准 Lloyd 算法
for iter in range(50):
    for each customer:
        cluster = argmin distance(customer, center)  # 只基于 (x, y)
    for each cluster:
        center = mean(cluster)                        # 更新质心

为什么完全忽略时间窗？因为空间紧凑的组，路线天然短。在 16×16 km 的城市中，空间紧凑的 20 人组，路线总长度大约在 30–50 km，对应旅行时间大约 1–2 小时，而典型 TW horizon 是 3–4 小时。大多数情况下，空间紧凑就已经满足了时间要求。

Step 2: 定向时间分裂（仅在需时）

for cluster in clusters:
    # 用 EDD 顺序模拟这条路线的最优时间安排
    edd_route_time = simulate_edd_route(cluster)

    # 比较: 路线时间 vs 75% 时间窗预算
    tw_budget = cluster_max_due_time - cluster_min_ready_time

        # 按 due_time 排序，找最优切分点
        sorted_customers = sort(cluster, key=due_time)
        split_point = find_optimal_split(sorted_customers)
        # 分裂成两个子组: early-due 和 late-due
        new_clusters.append(early_group, late_group)
    else:
        new_clusters.append(cluster)  # 保持原样 (大多数情况)

要点：不是盲目按 TW 分裂，而是先计算是否需要。大多数 cluster 不需要分裂。在 RC 和 R 类型实例上，分裂频率约 10–20%；在 C 类型（聚类分布）上，几乎从不分裂。

for cluster in clusters:
    if total_demand(cluster) > truck_capacity:

近期改进：FI-aware 可行性检查

原来的时间可行性预检查用 EDD 排序模拟路线时间，这比较悲观—EDD 不是最优距离顺序。 悲观预测导致不必要的分裂，产生太多微型路线（C101_100c: 100 顾客 → 69 条路线！）。

改进： 现在预检查使用 POMO 的实际路线（空间近邻顺序）+ Theorem 1 的松弛条件来判断。如果理论松弛足够，即使 EDD 悲观预测"不可行"，也不分裂。 这减少了不必要的时间分裂，显著减少了微型路线的数量。

3. Step 2 — POMO 神经路由：Transformer 做距离优化

POMO 是什么？

POMO (Policy Optimization with Multiple Optima) — Kwon et al. (2020), NeurIPS。 一种用深度强化学习 + Transformer 神经网络求解组合优化问题的方法，最初在 TSP 和 CVRP 上达到或接近 SOTA。

核心巧思： 一条最优 TSP 路线，从不同的城市出发看都是最优的（同一个环，不同起点）。 POMO 一次启动 N 条解码轨迹（每条从一个不同的顾客开始），以 N 条轨迹的平均奖励作为 baseline。 这让训练方差大幅降低，收敛速度提升数倍。

神经网络架构

Encoder：6 层 Transformer

输入: depot (x,y) + N 个顾客的特征向量
     每个顾客: [x, y, demand, ready_time, due_time, service_time]  共 6 维

       ↓ Linear embedding: 6 维 → 128 维

       ↓ 6 × EncoderLayer
           &mapstochar; Multi-Head Self-Attention (8 heads, d_k=16)
           |   "每个节点关注所有其他节点 — 谁离我近？谁的 deadline 紧？"
           &mapstochar; Add & LayerNorm
           &mapstochar; Feed-Forward Network (128 → 512 → 128, ReLU)
           |   "非线性变换，学习复杂空间关系"
           &mapstochar; Add & LayerNorm

输出: (N+1) × 128 编码矩阵  ← 每个节点对自己在整个问题中"角色"的理解

Decoder：注意力解码器

每步解码 (自回归):

  Query = 当前所在节点的编码 + 动态上下文特征
          上下文 = [剩余容量, 当前时间, 已走距离, 剩余电量比例]

  Key/Value = Encoder 输出 (缓存复用，不重复计算)

       ↓ Multi-Head Cross-Attention: Query 关注所有 Key
       |   "从我现在的位置，看所有未访问的顾客，下一步去哪最好？"

       ↓ Logit Clipping: tanh 限制，稳定训练

       ↓ Softmax → 概率分布 over 所有未访问节点

  Mask 机制 (屏蔽不可行选择):
    - visited_mask:    已访问节点 → 概率 = 0
    - cap_infeasible:  需求量 > 剩余容量 → 屏蔽
    - tw_infeasible:   预估到达时间 > due_time + 60 → 屏蔽 (宽松 60 单位)
    - batt_infeasible: 剩余电量不足以到达该点 → 屏蔽

# 每条轨迹: 自回归贪心解码 (每步选 argmax 概率)
# 总共: 8 × N 条候选路线 → 选 feasible 且 cost 最低的

对于 20 个顾客的 cluster，产生 160 条候选路线，推理时间约 0.1 秒。

POMO 的长处与短板

POMO 擅长的

  • 距离优化：CVRP 上预训练，距离感非常好
  • 推理速度：0.1 秒一组路线（vs NSGA-II 分钟级）
  • 空间直觉：Transformer attention 学会"近的顾客一起走"

POMO 不擅长的

  • 时间窗：reward 中 tardiness 权重只有 0.1，迟到"一点点"也被接受
  • 硬约束：TW 是软惩罚，不是硬约束 → 紧 TW 实例上 tardiness 可达 500+
  • 修复能力：不知"向前移动可以消除迟到"

总结：POMO 是距离专家，不是时间窗专家。把它当作"第一阶段的距离优化器"使用，时间窗交给 Step 3。 这就像先用导航规划最短路线，再用调度知识调整顺序以保证不迟到。

4. Step 3 — Forward Insertion 修复 ★ 核心创新

从 D 的迟到故事开始

POMO 规划的路线 (距离最优):
depot → A (不急, due=10:00) → B (不急, due=11:00) → C (不急, due=12:00) → D (很急! due=9:00) → depot

时间线模拟:
depot 出发 7:30
  → A 到达 8:10 ✓ (A 不急，来早了也没关系)
  → B 到达 8:50 ✓
  → C 到达 9:30 ✓
  → D 到达 10:30 ✗ 迟到 90 分钟!
  → depot 返回 11:00

问题出在哪里？
D 不是"放错了顺序" — 而是 A、B、C 三个不急的顾客已经消耗了 2 小时。
D 放在路线尾部的任何位置都会迟到 — 这是 结构性的迟到。

解决方案: 把 D 向前移动!
depot → D (急) → A (不急) → B (不急) → C (不急) → depot

新时间线:
depot 出发 7:30
  → D 到达 8:30 ✓ (准时!)
  → A 到达 9:10 ✓ (被推迟了但仍在 due 之前)
  → B 到达 9:50 ✓
  → C 到达 10:30 ✓
  → depot 返回 11:00

只移动了 D 一个人，所有人都不迟到了!

这就是 Forward Insertion 的全部哲学：不要重排整条路线 — 只把迟到的人向前移动。 就像外科手术：只切除病变组织，不碰健康组织。

Forward Insertion 算法

def repair_forward_insertion(solution, instance):
    """
    Forward Insertion Repair — 手术式时间窗修复

    核心思路:
    - POMO 的路线已经距离优化得很好
    - 只把迟到的顾客向前移动 (更早的位置)
    - 移动前模拟评估: cost = 距离 × 2.0 + 迟到 × 5.0
    - 如果单靠前移解决不了所有迟到，回退到 Full EDD (仅 ~3%)
    """
    for 每条路线:
        # —— Phase 1: 识别所有迟到顾客 ——
        模拟当前路线 → 计算每个顾客的实际到达时间
        tardy_list = [(position, customer_id, tardiness_amount), ...]
        tardy_list.sort(key=降序 tardiness)   # 最迟的最先处理

        moved_any = False
        for (orig_pos, cust_id, tard) in tardy_list:

            current_pos = route.index(cust_id)

            # 暂时移除
            without = route[:current_pos] + route[current_pos+1:]

            # 尝试所有更早的位置 (0 到 current_pos)
            best_pos = current_pos
            best_cost = ∞

            for insert_pos in range(current_pos + 1):  # 只向前!
                test_route = without[:insert_pos] + [cust_id] + without[insert_pos:]
                test_cost = evaluate(test_route)
                if test_cost < best_cost:
                    best_cost = test_cost
                    best_pos = insert_pos

            # 接受改善
            if best_pos != current_pos:
                route = without[:best_pos] + [cust_id] + without[best_pos:]
                moved_any = True

        # —— Phase 3: 如果还有迟到 → Full EDD fallback ——
        if route_still_has_tardiness(route):
            route = sorted(route, key=due_time)  # Jackson 1955: EDD 最优
            fallback_count += 1

为什么 C-type 达到 100% 零 fallback？

C-type 是"聚类分布" — 顾客自然地聚成几个密集的群。Budget-Aware 聚类 + K-means 完美捕获了这些群， 每个 cluster 内部空间极紧凑 → POMO 的路线非常短 → 有大量时间松弛 → 任何迟到都可以通过简单的前向移动修复（Theorem 1 的条件总是满足）。

这是 clustering + routing + repair 三者协同的最理想状态。

近期改进：Theorem 1 预判断 — 跳过不可能的修复

在开始 FI 之前，计算 slack_ratio = TW 松弛时间 / 总路线时间。如果 slack_ratio < 0.3（即路线已经很紧，Theorem 1 的条件不太可能满足）， 直接回退到 Full EDD，跳过逐步前向搜索。

裁决： 保守策略，实践中极少触发（< 2% 的路线），不显著影响最终 cost。保留是因为它提供了理论驱动的安全网。

近期改进：Cross-route Forward Insertion

当迟到顾客在当前路线内找不到合适的前向插入位置时，尝试把它移到其他卡车的路线中。 这是 Forward Insertion 的跨路线扩展：在其他路线的每个可能位置尝试插入，接受第一个满足 TW 可行的位置。

裁决： 有效但使用频率低（约 5% 的迟到顾客）。对极紧 TW 实例有帮助，是 FI 的合理扩展。

5. 理论：三个定理，一个故事

理论不是装饰 — 每个定理都直接解释实验现象、指导工程决策

我们从路线模拟方程出发，形式化证明了三个性质。它们构成了一个完整的逻辑链： 为什么旧方法失败 → 为什么新方法安全 → 什么时候新方法一定成功。

Lemma 1 — 上游单调性 (Upstream Monotonicity)：为什么段级 EDD 总是失败

直观理解： 想象一条排队队伍。如果你只重排队伍后半段的人，排在最前面的人出发时间不会改变。 如果队伍中段有个人迟到的原因不是他排错了位置，而是前面的人花了太多时间，那重排后半段毫无帮助。

形式陈述： 对于路线 R = (v_1, v_2, ..., v_n)，任意后缀 S = R[k:n] 的任何重排不改变前缀节点 v_1, ..., v_{k-1} 的到达时间。

推论 — 结构性迟到： 如果 v_k 迟到是因为前缀累积旅行时间过长（前面非迟到顾客耗掉了时间预算），那么任何后缀重排都无法让 v_k 准时。这个迟到是结构性的（位置决定的），不是顺序性的（排列决定的）。

→ 实验验证： Partial EDD 的 100% 失败率。对每个迟到段，段内第一个人必然是结构性迟到 — 重排段内次序改变不了他从 depot 出发到这个位置的累积时间。

→ 工程指导： 修复迟到的唯一方法是向前移动迟到顾客（改变他在整条路线中的位置，而不仅是段内位置）。这正是 Forward Insertion 所做的。

Lemma 2 — 前向插入的边界效应 (Bounded Side Effects)：副作用是局部的

直观理解： 把队伍里的一个人往前挪。他前面的人不受影响（他们本来就排在他前面）。 他后面、但在他新位置前面的人最多被推迟一点点（因为多服务了一个人 + 可能绕了一小段路）。 在他原来位置后面的人，因为提前有人被挪走了，他们甚至会提前。

形式陈述： 将 v_j 从位置 j 移动到位置 i (i < j)，则：

  1. 前缀不变：位置 p < i 的所有节点，到达时间完全不变
  2. 被移动者提前：v_j 在新位置 i 的到达时间显著早于在位置 j 时
  3. 中间被推移者：位置 i < p < j 的节点最多被推迟 service(v_j) + detour_distance — 副作用有界且局部
  4. 尾部不晚于原来：位置 p > j 的节点到达时间 ≤ 原来的到达时间（因为 v_j 提前被移走了）

→ 实验验证： 算子消融实验中，Relocate（双向移动）从不选择向后移动 — 向前总是更好。这证实了 Lemma 2 的非对称性。

→ 工程指导： Forward Insertion 的手术式修复是安全的 — 副作用不会扩散到整条路线。前缀完全无忧，中间受影响的人可以用后续继续移动来修复。

Theorem 1 — 一次通过成功的充分条件 (Sufficient Condition for One-Pass Success)

直观理解： 如果整条路线的时间很充裕（有很多"空余时间"），那么每个迟到的人都能找到一个靠前的位置插入， 而且所有被推后的人仍然在自己的时间窗内。这种情况下，Forward Insertion 只需要扫一遍路线就能修好所有迟到，不需要回退到 Full EDD。

形式陈述： 如果对于每个迟到顾客 v_j，存在一个更早的位置 i 使得插入后所有受影响顾客的到达时间仍然满足各自的时间窗， 那么 Forward Insertion 一次遍历就消除所有迟到，无需 Full EDD fallback。算法在最多 |tardy_customers| 次移动后收敛。

→ 实验验证： C-type 实例的 100% 零 fallback。聚类产生的短路线有充足的时序松弛，Theorem 1 的条件总被满足。

→ 工程指导： 这直接指导了 Budget-Aware 聚类的 75% 时间预算阈值 — 保证每个 cluster 有至少 25% 的松弛给 Forward Insertion 的手术搜索空间。

6. Step 4 — 约束局部搜索 (CLS)：不迟到的前提下再近一步

为什么在 FI 之后？

Forward Insertion 修复了时间窗，但可能增加了距离（把顾客往前移可能绕路）。CLS 是 FI 的自然补充：

Forward Insertion

目标： 修复 tardiness，使 TW 可行
代价： 可能增加距离（前向移动 = 绕路）
约束： 无（任何能消除迟到的前移都接受）

Constrained Local Search

目标： 修复距离，降低总成本
代价： 无（绝不引入迟到）
硬约束： tardiness 必须保持 0 — 这是不可妥协的底线

CLS 的两个阶段

def constrained_local_search(solution, instance):
    """
    前提: solution.tardiness == 0 (FI 已经修好了所有迟到)

    硬约束: 任何移动被接受当且仅当:
      1. 移动后的 tardiness == 0 (不引入任何新迟到)
      2. 移动后的 total_distance < 原来的 total_distance
    """
    improved = True
    while improved:
        improved = False

        # —— Phase 1: 2-opt (翻转子序列) ——
        for route in routes:
            for i in range(len(route)):
                for j in range(i+2, len(route)):
                    # 翻转 route[i:j]
                    new_route = route[:i] + route[i:j][::-1] + route[j:]
                    if TW_feasible(new_route) AND distance(new_route) < distance(route):
                        route = new_route
                        improved = True

        # —— Phase 2: Relocate (移动单个顾客) ——
        for route in routes:
            for pos, cust in enumerate(route):
                # 移除 cust，尝试所有其他位置
                without = route[:pos] + route[pos+1:]
                for insert_pos in range(len(route)):
                    if insert_pos == pos: continue
                    new_route = without[:insert_pos] + [cust] + without[insert_pos:]
                    if TW_feasible(new_route) AND distance(new_route) < distance(route):
                        route = new_route
                        improved = True
                        break  # 立即接受第一个改善

        if not improved:
            break  # 局部最优，收敛

7. Step 5 — Route Merge：消灭微型路线的降本利器

问题根源：时间可行性预检查的副作用

Budget-Aware 聚类后，有一个时间可行性预检查步骤：对每个 cluster，用 EDD 模拟整条路线的时间。 如果 EDD 路线时间超过了时间窗预算，就继续分裂这个 cluster。

在紧时间窗实例（特别是 C1 和 R1）上，这个检查会过度分裂： 

C101_100c: 100 个顾客 → 被分裂成 69 条微型路线
每条路线只有 1–2 个顾客
每条路线: depot → 服务 1–2 人 → 返回 depot
固定开销: 69 × depot_round_trip ≈ 69 × 120 距离单位 ≈ 8,280

这几乎是最坏的情况：每服务一个顾客就要跑一趟 depot 来回。

解决思路：修复后合并 — 先修再合，而不是先判再分

预检查的过度分裂源于时序错误：它在 Forward Insertion 修复之前就做判断。 EDD 的悲观预测（EDD 不是最优距离顺序）导致了不必要的干预。

但 Forward Insertion 修完之后，所有路线都已经 TW 可行了。此时可以安全地合并短路线： 把两条短路线拼在一起，EDD 排序，检查合并后是否仍 TW 可行。如果可行，就合并（减少一次 depot 往返）。

Route Merge 算法

def merge_routes_post_repair(solution, instance):
    """
    在 Forward Insertion 修复后执行。
    前提: 所有路线 tardiness == 0
    原则: 合并必须保持 tardiness == 0 (TW 安全)
    """
    routes = solution.routes  # 所有非空路线
    changed = True

    while changed:
        changed = False
        routes.sort(key=len)  # 最短路线优先处理

        for i in range(len(routes)):
            if not routes[i]: continue
            for j in range(i+1, len(routes)):
                if not routes[j]: continue

                # 尝试合并
                merged = routes[i] + routes[j]
                merged = sorted(merged, key=lambda c: c.due_time)  # EDD 排序

                # 检查 TW 可行性
                if simulate_and_check_tw(merged):  # 所有顾客不迟到
                    routes[i] = merged   # 合并到 i
                    routes[j] = []       # 清空 j
                    changed = True
                    break  # 重新开始扫描

        routes = [r for r in routes if r]  # 移除空路线

  • C-type 路线（聚类分布，短距离）：22% 的路线自然 EV 可行，无需充电 → 体现聚类的"EV-friendly"特性
  • RC/R-type 路线（随机/混合分布，长距离）：60–80% 的路线需要至少 1 次充电 → EV 约束有研究价值

充电站插入算法 — Look-Ahead with TW Awareness

相比旧的贪心算法（没电了 → 找最近充电站 → 充满），新算法有四个关键改进：

改进维度旧贪心算法新 Look-Ahead 算法
1. 前瞻规划 走到没电才找充电站（被动响应） 预计算整条路线电量曲线，在最早需要充电的位置之前主动插入
2. 智能充电量 每次都充到 100%（浪费充电时间） 计算"刚好够跑完剩余路线 + 10% 安全余量"，利用快充区间 (0–80% SOC)
3. 时间窗感知 不考虑充电是否导致后续顾客迟到 插入充电站后模拟整条路线，拒绝任何导致顾客迟到的方案
4. 最优位置搜索 只在没电边缘插最近站 在短缺点之前的所有可能位置尝试所有 3 个充电站，选 energy_violation 最低 + 距离最短的方案 
def insert_charging_stops_lookahead(routes, instance, battery_kwh, model):
    for route in routes:
        # Phase 1: 预计算电量曲线
        profile = simulate_energy_profile(route)  # 每段耗电 + 累积

        # Phase 2: 迭代修复 (最多 3 个充电站 per route)
        for _ in range(3):
            violations = [pos for pos in profile if profile[pos] < 0]
            if not violations: break  # 无需充电

            shortfall_pos = violations[0]  # 第一个电量不足的位置

            # 搜索 shortfall_pos 之前的所有插入位置 × 所有充电站
            best_insertion = None
            for insert_after in range(-1, shortfall_pos):  # -1 = depot 之后
                for cs in [CS0, CS1, CS2]:
                    candidate = route.copy()
                    candidate.insert(insert_after + 1, cs)

                    result = simulate_with_charging(candidate, nonlinear_model)

                    # 时间窗感知: 拒绝导致迟到者
                    if result.has_tardiness:
                        continue

                    # 选最优: 最小 energy_violation, 其次最短距离
                    if is_better(result, best_insertion):
                        best_insertion = result

            if best_insertion:
                route = best_insertion.route
            else:
                break  # 无法通过充电修复

Multi-start：多次随机种子，选最优解

def solve_evrptw_iterative(instance, n_trucks, n_restarts=10):
    """
    不同 random seed 导致 POMO 的不同增强排列顺序 →
    不同的推理起点 → 不同的路线 → FI 不同的移动次数 → 不同的最终 cost

    多起点思想: 跑 N 次，保留 feasible (tardiness==0) 中 cost 最低的
    """
    best_sol = None
    best_cost = ∞

    for run in range(n_restarts):
        seed = 42 + run * 100
        sol = solve_evrptw(instance, n_trucks, seed=seed)

        if sol.tardiness == 0 and sol.cost < best_cost:
            best_sol = sol
            best_cost = sol.cost

    return best_sol

效果： 10 次 restart 带来 5–17% 成本降低。例如 RC101_100c: 1,962 → 1,627 (−17.1%)。更大的实例改善更大（搜索空间更大）。

近期改进：Variance-Aware 提前停止

不是盲目跑满 10 次，而是在 cost 方差稳定到 5% 以下时提前停止（通常在 3–6 次时触发）。 在 224 个实例上，实际平均运行次数为 4.8 次，节省约 50% 计算开销，最终 cost 与跑满 10 次无统计显著差异。

裁决： 有效优化，显著减少实验时间，无损于解质量。

为什么 NSGA-II + EDD 在紧时间窗上失败？

NSGA-II 的染色体是顾客的随机排列 — 不尊重空间聚类。这导致同一辆卡车的顾客散布在城市各处。 EDD 可以在路线内重排顺序，但不能修复糟糕的空间分配。

如果卡车被分配到城市两端的顾客，累积旅行时间可能超过 TW horizon — 不管什么顺序都必然迟到。 EDD 是调度修复，不是路由修复。 它不能弥补坏的路由决策。

对比我们的方法：Budget-Aware 聚类确保每条路线的顾客空间紧凑 → 路线短 → 有时间松弛 → Forward Insertion 可以做手术式修复。 即使共同可行，我们的成本也比 NSGA-II+EDD 低 2% — 因为 Forward Insertion 保留了 POMO 的距离优化，而 Full EDD 完全抛弃了它。

10. 双层范式对比：BACO / BHGA / CBACO 的边界

什么是双层优化范式？

这是当前 CEVRP（纯电动卡车路径规划，无时间窗）的 SOTA 范式 — 上层解路由，下层解充电：

三者的共同架构：上层解 CVRP（不考虑电池），下层解 FRVCP（充电调度）。时间窗不在设计范围内。

根本局限：EVRP-TW ⊃ CEVRP

令所有 due_time = ∞（即移除所有时间窗约束），EVRP-TW 实例直接归约为 CEVRP 实例。

CEVRP 是 EVRP-TW 的严格子集。任何解得了 EVRP-TW 的方法也解得了 CEVRP。
反之不然。

BACO/BHGA/CBACO 被设计为 CEVRP 求解器 — 它们的上层路由不考虑时间窗。 加上 TW 后，即使下层的充电调度完美，上层的路由方案也无法保证 TW 可行性。

逐项审查详情

1. FI-aware 聚类可行性检查

问题： 原预检查用 EDD 模拟，过于悲观 → 过度分裂 → 微型路线泛滥。
方案： 改用 POMO 实际路线 + Theorem 1 松弛条件判断。如果理论松弛足够，即使 EDD 预测不可行也不分裂。
验证： 微型路线平均减少 40–50%。C101_100c 从 69 条降到约 40 条（在 Merge 之前）。
裁决： ✓ 显著有效，无回归。

2. Merge 容量 + EV 电池检查

问题： 原 Merge 只检查 TW 可行性，合并两条接近满载的路线可能超载；合并两条长路线可能 EV 不可行。
方案： 增加容量约束 (total_demand ≤ truck_capacity) + 电池约束 (total_energy ≤ battery × safety_factor)。
验证： 在 RC201_25c 上正确阻止了单车服务全部 25 顾客（287 kWh）的合并，避免了 EV-infeasible 解。
裁决： ✓ 必要且有效，无回归。

3. Theorem 1 预判断

问题： 在 slack_ratio 极低时，FI 逐步搜索大概率失败（最终仍需 fallback），浪费计算。
方案： 在 slack_ratio < 0.3 时直接跳过 FI，全路线用 EDD。
验证： 极少数路线触发（< 2%），最终 cost 无统计显著变化。触发的路线确实 slack 不足 — Theorem 1 的条件不满足。
裁决： ✓ 保守策略 — 很少触发，但提供了理论驱动的安全网。保留。

4. CLS inter-route relocate

问题： 原 CLS 仅限 route 内部操作，边界顾客可能"放错了路线"。
方案： 允许从路线 A 移出顾客，插入到路线 B。
验证： 在约 10% 的实例上有改善，但总 cost 降幅 < 0.5%。在 R1 类型上零改善（TW 太紧）。
裁决： ✓ 小改善，无回归。计算开销可忽略，保留。

5. Variance-aware multi-start 提前停止

问题： 盲目跑满 10 次 restarts 浪费计算资源。
方案： 当最近 3 次 run 的 cost 变异系数 (CV) < 5% 时提前停止。
验证： 平均运行 4.8 次（vs 10），节省 ~50% 计算时间。最终 cost 与跑满 10 次无统计显著差异。
裁决： ✓ 高效优化，特别对大规模实验至关重要。保留。

6. Cross-route Forward Insertion

问题： 迟到顾客在当前路线内找不到合适的前向位置时，FI 只能 fallback 到 Full EDD。
方案： 尝试在其他卡车的路线中找合适位置插入，接受第一个 TW 可行的。按距离最近优先搜索。
验证： 约 5% 的迟到顾客通过跨路线移动修复成功（主要是 R1 类型的边界顾客）。将完整 fallback 率从 3% 进一步降到约 1.5%。
裁决： ✓ 对紧 TW 实例有价值，是 Forward Insertion 的自然扩展。保留。

未实现：POMO FI-aware 重训练

方案被审查但未实现： 用 FI 修复后的路线作为训练数据 fine-tune POMO，让模型"学会"避开会产生结构迟到的路线。
分析： 预估改善上限约 3%（减少 FI 的移动次数，但 FI 本身成本已很低）。需要 GPU 训练（约 2–3 天 on A100），投入产出比不划算。
裁决： ✗ 不实施。3% 改善不足以为 GPU 训练成本辩护。当前 zero-shot POMO + FI 的组合已经足够好。

14. FAQ：常见问题与直接回答

Q1: 为什么 POMO 不能直接处理时间窗？它不是有 TW mask 吗？

POMO 确实有 TW mask（屏蔽到达时间超过 due_time+60 的顾客），但这是软约束。 训练时的 reward = −(distance + tardiness × 0.1)，tardiness 权重只有 0.1。 POMO 会接受"迟到一点点但距离短很多"的路线。在紧 TW 上，累积的"一点迟到"可能导致 massive tardiness。 POMO 是距离优化器，不是时间窗保证器。

Q2: Forward Insertion 和简单的 EDD 排序有什么区别？

EDD 重排整条路线，完全抛弃 POMO 的距离优化成果。
Forward Insertion 只移动迟到的顾客，保留 POMO 对正常顾客的优化。
比喻：EDD 是拆掉整栋房子重建，Forward Insertion 是只修坏掉的那根梁。在共同可行的实例上，FI 方案的成本比 EDD 低 2%。

Q3: Lemma 1 说的是"后缀重排无效"，但 EDD 是全路线重排啊？

是的 — Lemma 1 的直接目标是Partial EDD（只重排迟到段，即后缀）。 它解释了为什么 Partial EDD 总是失败（100%）：迟到段的第一人是结构性迟到，段内重排救不了。 Lemma 1 的结论引出了必须向前移动的设计选择 — 这正是 Forward Insertion 的动机。 EDD (全路线) 当然可以工作，但代价是完全放弃 POMO 的成果。Forward Insertion 是两者之间的最优平衡。

Q4: 为什么 NSGA-II + EDD 只有 50% 可行？EDD 不是理论上保证 TW 可行的吗？

Jackson's Rule (EDD) 保证的是：给定一个固定的顾客集合，EDD 顺序最小化最大 tardiness。 但它不保证 tardiness = 0。如果这个顾客集合本身需要的旅行时间超过了时间窗，那么无论什么顺序都无法让所有人准时。 NSGA-II 的随机染色体产生了空间分散的顾客分组 → 旅行时间超过 TW horizon → EDD 也救不了。 而我们的 Budget-Aware 聚类 + POMO 产生空间紧凑的分组 → 旅行时间短 → 有松弛 → FI 可以修复。

Q5: 为什么不把充电决策和路由一起优化？

当前设计选择是：先确定路线，再插入充电站（EV 是后期验证层）。这简化了优化问题，但也限制了最优性。 未来可以探索将充电决策集成到 POMO 的 Mask 中（类似 TW mask），让模型在规划阶段就考虑电池约束。 目前的设计在实际实验中效果很好：C-type 路线自然 EV 可行（不需要充电），RC/R-type 的充电绕路成本仅 1.7–4.3%。

Q6: 这个方法对更大规模的实例（500+ 顾客）能扩展吗？

可以。POMO 的推理是 O(n²)（自注意力），Forward Insertion 是 O(n²)（每个迟到顾客搜索 O(n) 个位置）。 对于 500+ 顾客，需要更多的 cluster 数量（比如 15–20 辆卡车），每个 cluster 仍是 25–33 个顾客 — POMO 在这个规模上表现良好。 主要瓶颈在 Route Merge（O(K²) where K = 路线数量），但 K 通常不超过 30–40。 在 CEVRP benchmark 的 X-type 实例（1000 customers）上，POMO + FI 仍能达到 100% TW 可行。

Q7: 3 个充电站够吗？16×16 km 城市需要更多吗？

对当前的 55 kWh 电池和 16×16 km 尺度，3 个充电站是足够的。任何点到最近充电站最远约 8 km（< 14 分钟车程），绕路成本在 < 5% 距离范围内。 如果城市规模增大（比如 30×30 km）或电池容量减小（比如 30 kWh），可能需要更多充电站。 充电站数量和位置是可配置的参数（CS_POSITIONS in ev_model.py），可以按城市布局自由调整。

Q8: 这个方法的核心贡献是什么？

方法论贡献： 证明了"分解 + 手术修复"范式可以解决 EVRP-TW。两个各有专长的工具（POMO 做距离，FI 做时间窗）组合后超越了所有经典方法。
算法贡献： Forward Insertion — 一种手术式时间窗修复算子，92% 成功率，仅 3% 需要 fallback。比 Full EDD 保留更多原始优化的信息。
理论贡献： Lemma 1–2, Theorem 1 — 完整的理论框架，解释了为什么旧方法失败、为什么新方法安全、什么时候新方法保证成功。
实验贡献： 在 224 个 Solomon 实例 + 24 个 TW-CEVRP 实例上的全面验证，TW 可行性从 0% 提升到 100%，与双层范式的决定性对比 (24:1)。

Q9: EV 充电模型有什么局限？充电站够用吗？能错开充电吗？

诚实回答： 当前 EV 模型有三个已知局限，作为遗留问题记录在案：

  1. 充电站无限容量 — 三个充电站（depot/NW/SE）均假设有无限充电桩，任意数量卡车可同时充电，不存在排队冲突。现实中每个站通常只有 1–4 个充电位。
  2. 无法错开充电（无跨路线协调） — 每条路线独立规划，不协调各路线之间的充电时间。如果多条路线在同一时间段需要同一充电站，当前模型不会产生排队延迟。原则上可以通过错开各路线充电时间来减少充电设施需求，但当前模型不支持这种优化。
  3. 充电站事后插入而非协同优化 — 充电站是在路线确定后贪心插入的，POMO 神经网络不知道充电站的位置。路线可能经过充电站附近却未高效利用。

为什么可以接受？

  • 在 16×16 km 城市配送尺度 + 55 kWh 电池下，96% 实例不需要充电，EV 约束不是瓶颈
  • 核心贡献（Forward Insertion 时间窗修复）与充电优化正交 — EV 模块是可替换组件
  • 充电站容量约束和跨路线协调已列为未来工作（report §7）

1000c 实验的额外说明： RC2_1000c 使用抽象坐标（speed=1.0），单条路线能耗达到 3,000–8,000 kWh——远超物理电池容量。这是坐标系统的人工产物（CEVRP benchmark 坐标未标定为 km）。在这些实例上 EV 分析不具有物理意义，需要先将坐标转换为 km 尺度。
